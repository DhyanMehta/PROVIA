# First-party authentication migration

Audit baseline: d800158; backend revision 0004; 21 application tables. Existing ownership is `users.id`; `users.auth_provider_subject` is the unique legacy provisioning key. `users.email` is mutable, nonunique contact data and is never credential proof.

Implementation: additive revision 0005 adds accounts, session families, refresh-token history, purpose-bound actions and shared abuse-control buckets. Preserve all existing users and foreign keys. New accounts get a new internal UUID and reserved `provia:<uuid>` legacy-column marker; authentication never resolves or provisions by that marker. No email-based merging. Registration matching a legacy contact is held for an operator-assisted ownership claim; it never overwrites or claims the existing record. Legacy enrollment requires separately verified old-account ownership and an explicit operator action; that workflow is not an email password reset.

Access JWTs: HS256 only, server-only >=256-bit random secret, required issuer/audience/sub/sid/jti/iat/nbf/exp/type, 15-minute default lifetime. Each request also checks persisted account and session revocation/expiry. Refresh: 256-bit opaque random token, SHA-256 digest only, 30-day absolute family lifetime, account→family→token locking, atomic rotation and family revocation on replay. No retry of uncertain rotation; mobile single-flight refresh and session-generation guards fail closed.

Passwords: maintained argon2-cffi Argon2id, 19MiB/2 iterations/1 lane, maximum two hash operations per process, 15–128 Unicode characters and <=512 UTF-8 bytes. Preserve password whitespace and Unicode exactly. Normalize email separately. Login errors are generic; database-backed HMAC-keyed account and IP buckets persist failed attempts. Raw forwarded headers are untrusted unless the immediate proxy belongs to an explicit trusted network.

Email policy: verification is mandatory for fitness data. Login to a pending account can manage verification/account status only. Optional Resend HTTPS delivery supports Render Free, which blocks standard SMTP ports; a verified-TLS SMTP adapter is also available where permitted. The user must configure a permitted sender; missing delivery blocks issuance. No development token-return endpoint. Tests inject an in-memory delivery adapter, never enabled by runtime configuration. One-time actions are hashed, expiring, atomic and purpose-bound. Reset/change revoke all sessions. Security counters/replay revocations commit before error responses, avoiding existing get_db rollback semantics.

Phases: implement and test backend additively; integrate mobile and generated contracts; replace runtime provider only after testing; validate migrations in disposable PostgreSQL; prepare cutover/rollback. No deployment, existing-database migration, live-credential removal, phone-data reset or cloud build is authorized in this step. Existing EAS identity/signing configuration is preserved.
